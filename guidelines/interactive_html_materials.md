- 適用：制作ガイドライン第7.1節に基づき、静的HTML教材の複数環境共用方式を採用する作品

## 1. 採用条件と構成

以下は2026-11のRPG教材で検証した方式。HTML/CSS/JavaScriptの静的教材に適用し、外部ライブラリ・モジュール・サーバーAPI・ビルドが必要な作品は個別に成立条件を確認する。

```text
src/public/
  index.html                     教材一覧
  presentations/<chapter>/index.html
  examples/
    download.html                共通保存画面
    download.js                  共通保存処理
    <chapter>/<stage>/
      demo.html                  HTMLパネル兼単独起動
      demo.css                   スタイル
      demo.js                    実行処理
      demo.details               JSFiddleメタ情報
      index.html                 旧URL互換が必要な場合だけ
tests/                           公開対象外の検証コード
.github/workflows/               CI設定
```

ファイル名4種はJSFiddle GitHub読み込み方式の契約。各ステージの機能をこの4ファイルで一元管理する。GitHubの正式公開ブランチを正本とし、作業ブランチは検証用。公開Webサイトは作品の配備仕様に従う。RPGではsrc/publicのGit管理ファイルを無変換で配信する。別作品の配信方式を推測しない。

## 2. 実行環境と読み込み責任

| 経路 | CSS/JSの読み込み責任 | 確認事項 |
| --- | --- | --- |
| 公開Webサイト | demo.htmlの環境判定ローダー | ホスト名・HTTPS・相対URL |
| file:// | 同上 | UTF-8・相対ファイル・ローカル制約 |
| localhost / 127.0.0.1 | 同上 | VSCode Go Live相当のHTTP起動 |
| JSFiddle | JSFiddleのCSS/JSパネル | ローダーを起動せず、二重実行しない |

実コードは参照実装一覧のdemo.htmlを使用する。次はRPGで確認したローダーそのもの（ホスト名は対象作品の公開先に変更する）。

```html
<script>
  if (location.protocol === 'file:' ||
      location.hostname === 'localhost' ||
      location.hostname === '127.0.0.1' ||
      location.hostname === 'demo.sarajevo.jp') {
    document.write('<link rel="stylesheet" href="demo.css">');
    document.write('<script src="demo.js"><\/script>');
  }
</script>
```

- HTMLパネルの内容を単独HTMLとしても使う。ファイル先頭に `<!doctype html>` と `<meta charset="utf-8">` を置く。viewportは旧画面の指定を維持し、新規教材では対象端末に適合する値を設計する。
- CSS・JSを別ファイルへ分離し、DOM要素の定義後にローダーを置く。CSS・JSが不足せず、JSが一度だけ実行されることを検証する。
- `document.write` は当該方式の初回パース中の限定的な使用例であり、一般的な推奨APIではない。ユーザー入力を組み込まない。非同期・遅延実行、CSP等の制約、ホスト名判定の成立性を確認する。必要な場合は代替ローダーを設計し再検証する。
- JSFiddleの結果フレームと公開ホストが一致しないという条件に依存する。未登録ホスト・別のコード実行サービスで自動動作するとは保証しない。
- demo.detailsはJSFiddle用のメタ情報であり、コメント形式のnameとdescriptionを各教材に合わせる。

```text
/*
---
name: 教材名
description: 教材の説明
...
*/
```

## 3. 導線・公開ブランチ

教材一覧および必要な演習ページから、直接起動（demo.html）、JSFiddle、ダウンロードを提示する。RPGのJSFiddle GitHub読み込み形式：

```text
https://jsfiddle.net/gh/get/library/pure/<owner>/<repo>/tree/<branch>/src/public/examples/<chapter>/<stage>/
```

この形式はRPGの実サービスで代表確認済み。別作品のリポジトリ公開範囲・ブランチ・ファイル仕様を確認する。スラッシュを含むブランチ名での読み込みはRPGの試行で404となったため、検証用はスラッシュなしの名前を用いる。正式公開時はmain等の実際の正式ブランチに切り替え、統合前に公開用リンクが利用可能と断定しない。GitHubのソース参照リンクも同期する。

旧URLを維持する必要がある場合は旧index.htmlを同ディレクトリのdemo.htmlへ遷移するだけの互換ページにし、旧ゲーム本体との二重管理を解消する。旧JSへの直リンク等は影響調査の上で別途判断する。

## 4. 配布と保存

共通download.htmlとdownload.jsを各ステージから利用し、`?stage=<chapter>/<stage>` は定義した許容リストに一致する値だけ受け付ける。4ファイルを変換せず配信する。任意のURLやファイルパスをユーザー入力から生成しない。

- showDirectoryPickerが利用可能な環境ではユーザー操作からreadwriteで選択する。既存ファイルを列挙し、上書き確認で拒否されたら保存しない。
- 全4ファイルの取得成功を確認してから順次保存する。正常時は完了件数、途中失敗時は保存済み件数と失敗を通知する。部分保存はあり得るため、原子的な保存・ロールバックを保証しない。
- キャンセル、NotFoundError以外の取得エラー、HTTP失敗、書き込み失敗、不正な教材指定を区別する。新規実装の異常契約は正式採用規約に従う。
- フォルダ選択API非対応時はdownload属性付きリンクで個別保存できるようにする。一括クリックはブラウザの複数ダウンロード許可や端末制約に依存するため、個別リンクを残し、保存完了を推測で通知しない。取得したファイルの場所・存在を確認する。
- ZIP・変換処理は本方式では不要。作品固有要件があれば別方式を設計する。

実処理・画面の正本は参照実装一覧のdownload.js / download.html。別作品では許容ステージ、URL、表示文、ファイル仕様、失敗契約を調整し、改変版を再検証する。

## 5. 検証標準

制作ガイドライン第10.2・10.3節に従い、目的、成功/失敗/判定不能、手順、比較対象、回数、停止条件を定める。検証の粒度は変更影響と共通構造から判断する。

| 検査 | 期待結果 |
| --- | --- |
| 構造・リンク | 各ステージ4ファイル、メタ情報、許容リスト、起動・ソース・保存リンク一致。旧ソース重複なし |
| 構文・既存機能 | JS構文と既存契約、章間引き継ぎ等を必要範囲で確認 |
| 実ブラウザ | 標準文書モード、UTF-8、日本語表示、CSS/JS読み込み1回、初期化・主要操作・リセット、未処理JS例外なし |
| 環境差 | file://、ローカルHTTP、公開ホスト名、JSFiddle相当環境の差異。実サービス・実機操作は別記録 |
| 保存 | 各ファイルを取得し正本とバイト比較。上書き拒否/許可、キャンセル、取得失敗、不正指定、個別保存、書込失敗は対象に応じて検証 |
| 配備 | 固定SHA・作業ツリー・実際の配信内容を比較。旧URLを維持する場合は確認 |
| 公開操作 | 実際の公開URLから代表教材の起動、主要操作、JSFiddleへの遷移、保存結果を確認 |

RPGではGitHub ActionsのUbuntu 24.04、Node 22、Playwright 1.56.1、Chromiumで自動化した。Ubuntu latestが26.04となり当該Playwrightのブラウザインストールが失敗したため24.04を選択した。固定版を未来にわたり推奨するものではない。新規依存導入・更新は適用規約の承認と互換性・セキュリティ・ライセンス確認を経る。既存導入の承認証跡は [RPG Issue #6](https://github.com/Sarajevo001/oop-rpg-workshop/issues/6) で確認中。

実ブラウザのファイル保存テストはnative pickerをOPFSに置換した。保存されたバイト列は実測できるが、OSのダイアログ操作の証明ではない。JSFiddle相当テストは外部サービス自体を検証しない。CIからの実サービス403は判定不能とし、人の通常ブラウザで代表確認した。外部サービス診断は決定的な回帰テストから分離する。

## 6. 再利用・変更管理

作品ごとに採用環境・正本SHA・必要な変更・検証計画を記録する。参照実装の採用はコードや外部依存の無条件承認を意味しない。既存規約に矛盾・遵守不能・判定不能がある場合は該当規約の処置に従う。検証済みコードと新しく改変したコードを区別する。

完成時に、検証記録を作品リポジトリに残し、他作品にも有用な知見があれば制作ガイドライン・本技術標準・参照実装一覧の更新を提案する。正本の改訂は明示承認に基づいて行い、版と変更理由を記録する。
